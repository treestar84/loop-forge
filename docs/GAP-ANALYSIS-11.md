> 1회 즉흥 설계된 Opus봇보다 약한 NPC가 나오는 것은 말이 안 된다. 루프포지가
> **당연히 더 상위 난이도의 봇을 만들어내는 장치**가 되도록 놓친 구현 포인트를

## 0. 전제가 되는 실측 사실 (기존 문서 요약, 재측정 아님)

| 게임 | 루프포지 상태 | C열(Opus봇 승률) | 판정 |
|---|---|---|---|
| 스플랜더 v3 | 2/3 채택 | 11.3% | **루프포지 압도** |
| 윙스팬 v2 | 1/1 채택 | 24.3% | **루프포지 역전** |
| 하스스톤 v2 | 1/? 채택 | 66.9% | Opus 우세(접전) |
| 도미니언 v2 | near-miss 누적 | 95.3% (v1 문맥, 낡음) | Opus 우세 |
| 오목 v5 | 카드 5장 소진 | 100% (N=1,300) | Opus 완승 확정 |

스플랜더·윙스팬은 "루프포지가 Opus를 이길 수 있다"는 존재 증명이다. 따라서
문제는 프레임워크의 무능이 아니라 **특정 조건에서만 작동하는 구조적 갭**이고,
그 갭은 게임별 전술이 아니라 루프 설계 자체에 있다 — 이것이 이 라운드의 관점
전환이다(기존 오목 C열 5장 카드는 전부 "게임/탐색 수준"의 변주였다).

## 1. 근본 원인 — 루프 설계 수준의 결함 5가지

### R1. 루프의 목표 함수에 "외부 강자"가 없다 (가장 근본적)

작은 루프의 모든 게이트(smoke/prune/holdout/regression)의 대전 상대는
`WaveConfig.opponent: 'heuristic' | 'random'`(`src/loop/wave-runner.ts:68`)과
현 챔피언(regression 티어)뿐이다. `fieldMix`(M4)도 같은 두 종의 배열이다.
`BenchmarkAnchor`의 kind도 random/heuristic/frozen-baseline 3종뿐
(`src/artifacts/baseline-registry.ts`).

**즉 루프는 "내부 기준선 대비 개선"이라는 자기 정의 언덕만 오른다.** 이 언덕을
무한히 올라도 Opus봇을 이길 필요가 전혀 없다 — Opus봇 승률은 웨이브가 끝난 뒤
별도 벤치마크(관찰 전용)로만 측정되고, 다음 후보 설계에 기계적으로 피드백되지
않는다. 스플랜더·윙스팬의 승리는 내부 언덕과 외부 언덕의 방향이 우연히 일치한
경우다(IS-MCTS가 은닉 정보 처리라는 절대적 우위를 줬기 때문). 오목처럼 두 언덕이
갈라지는 게임(내부 기준선 완파 ↔ Opus 0%, GAP-8 §4.6의 mcts2-s256-cr가 정확히
이 사례)에서는 루프가 아무리 돌아도 Opus에 수렴하지 않는다. **최적화 장치는
목표 함수에 없는 것을 최적화하지 않는다.**

부속 결함(R1-b): 외부 계측이 있더라도 상대가 "고수 1명"뿐이면 두 가지 병리가
생긴다 — ① **무정보 손실 함수**: 현 오목 진단이 카드 1~5 전부 0%라 카드 간
우열조차 측정 불가(그래디언트 소실), ② **단일 상대 과적합**: 그 봇의 버릇을
공략하는 채택이 "즉흥 설계 LLM봇 일반"에 대한 실력 향상과 동일시될 위험.

### R2. 패배 데이터가 전부 버려진다

`runHeadToHead`(`src/loop/head-to-head.ts`)는 승률/CI/점수차만 반환하고
trajectory를 폐기한다. 오목에서 Opus봇에게 500판 이상을 졌지만(카드 1~5 진단
합산), "몇 수째에 무엇이 갈렸는가, Opus는 그 국면에서 무엇을 뒀는가"를 기계가
읽을 수 있는 형태로 남긴 기록이 0건이다. 큰루프 3단계(재설계)의 입력은
`extractNearMissCandidates`가 주는 내부 게이트 실패 통계뿐 — **외부 강자에게
진 이유는 매 라운드 사람이 정성 추정으로 재구성해야 했다**(GAP-8 §4.7의
도미니언 실패 원인 추정이 "정황 증거, 확정 아님"인 이유가 바로 이것이다).

### R3. 지식 주입 통로가 두 극단뿐 — 트리 정책에 prior가 없다

`src/search/mcts.ts:36` 주석이 스스로 명시한다: "No solver, **no policy prior**".
현재 게임 지식이 탐색에 들어가는 통로는 정확히 두 개다:

1. **롤아웃 정책**(`rolloutPolicy`/`rolloutFactory`) — 시뮬레이션 끝단의 평가에만
   영향. 카드 4의 실측: forkAwareness 순정 휴리스틱 9.0% → MCTS 롤아웃으로
   감싸면 0.0%. **희석된다.**
2. **루트 오버라이드**(`rootOverride`, tacticalDepth) — 루트 1수에만 영향.
   카드 5의 실측: 41.1% 발동에도 0.0%. **단발이라 수순 전체를 못 바꾼다.**

Opus봇의 우위(다방향 위협 스코어링)는 **매 노드의 수 선택 품질**이다. 이에
대응하려면 지식이 트리의 선택(selection) 단계 — UCB 항 — 에 들어가야 하는데
(AlphaZero의 PUCT, 체스 엔진의 progressive bias가 정확히 이 자리), 계약에도
탐색에도 그 주입점이 없다. 카드 1~5가 전부 실패한 것은 5번 모두 **지식을 넣을
수 없는 자리에 지식을 밀어 넣으려 한 시도**였기 때문이다 — GAP-8 §4.8이
"다방향 위협 스코어링을 서치 평가함수에 이식"을 남은 가설로 명시 이연한
바로 그 지점이다.

### R4. 큰루프 3단계(재설계)에 설계 품질·다양성 프로토콜이 없다

FIX-BACKLOG 스스로 인정한 원인: "지금까지의 전략 대부분이 빠르게 작성된 단순
휴리스틱이었지 오퍼스 수준의 깊은 설계 노력을 들인 게 아니었다." 벤치마크의
Opus봇에는 Opus급 모델의 집중 설계 1회가 들어갔는데, 루프포지 후보에는 그
수준의 노력 투입을 유도·강제하는 절차가 없다(비대칭 노력). 또한 후보 생성이
매 라운드 "그때 떠오른 한 가지 아이디어"의 직렬 시도라서, 활용(기존 개선)과
탐험(새 발상), 심층 설계(고비용 고품질)와 기계적 변형(저비용 다수)의 **배분
개념 자체가 없다** — DESIGN §7이 Optuna/Ax의 탐색-활용 균형을 "v2에서 참고"로
미뤄 둔 그 지점이 정확히 여기다.

### R5. 축(카드) 목록이 임기응변이라 루프가 일찍 멈춘다

"무수히 반복하는 장치"여야 하는데 오목은 5장, 도미니언은 3장 만에 카드가
소진됐다. ADR-0009(억지 반복 금지)는 옳은 원칙이지만, 그 적용 단위인 "축"의
목록 자체가 체계 없이 즉석 발굴되다 보니 금방 바닥난다. 미시도 축이 명시적
목록으로 존재하면(§3 D6) "같은 손잡이 반복 금지"와 "루프는 계속 돈다"가
양립한다 — 지금은 전자가 후자를 조기 종료시키는 구조다.

## 3. 처치 설계

설계 원칙: 기존 불변 규칙을 하나도 깨지 않는다 — 계층 의존 방향 유지, 앵커
갱신 금지(신규 앵커 **등록**은 허용이며 등록 후 봉인), holdout 뱅크 재사용 금지,
모든 신규 옵션은 미지정 시 기존 동작 byte-for-byte 불변(rolloutFactory·
tacticalDepth·rootOverride가 확립한 패턴).

### D1. 계약 확장 — `choiceEvaluator` (지식을 "데이터로 선언"하는 세 번째 통로)

`GameSpec`에 옵션 필드 추가:

```ts
/** 선택지별 정적 평가(높을수록 유망). 탐색 계층이 prior로 소비한다.
 *  strategySurface와 동일 원칙: 어댑터가 데이터로 선언, 커널/탐색은 실행만. */
readonly choiceEvaluator?: (
  state: TState, player: PlayerId, choices: readonly TChoice[],
) => readonly number[];
```

- 게임 지식은 여전히 어댑터(계층 ①) 안에 갇힌다 — search 계층은 숫자 배열만
  받는다. 의존 방향 위반 없음(`dependency-rules.test.ts` 그대로 통과해야 함).
- 오목의 forkAwareness 점수 함수(이미 존재, `gomokuForkDecision`의 판정 로직)를
  이 인터페이스로 재표현하는 것이 첫 실증이다.
- 되돌리기 비싼 계약 변경이므로 구현 시 **ADR-0011**로 기록.

### D2. `search/mcts.ts`에 PUCT prior + progressive bias (R3 처치)

`MctsConfig`에 옵션 추가(미지정 시 기존 동작 완전 불변):

```ts
readonly priorWeight?: number;   // 0 또는 미지정 = 비활성
readonly priorSource?: 'choiceEvaluator';  // v1은 어댑터 evaluator만
```

- 선택 단계 UCB 항을 `Q + uctC·sqrt(lnN/n) + priorWeight·P(c)/(1+n)`으로 확장
  (progressive bias — 방문이 쌓이면 prior 영향이 자연 감쇠해 통계가 지식을
  이긴다). `P(c)`는 choiceEvaluator 점수의 softmax.
- 확장(expansion) 순서도 prior 내림차순(prior 부재 시 기존 rng 셔플 폴백 유지).
- IS-MCTS는 MctsConfig를 재사용하므로(GAP-8 §4.7 확인 사실) 코드 공유 경로에서
  자동 적용 — 회귀 테스트로 고정.
- 단위테스트: 미지정 시 기존 trajectory 지문 완전 일치 / prior가 초기 방문을
  실제로 편향 / 대량 방문 후 Q 지배 / 결정론.

### D3. 앵커 래더 + 앵커 홀드아웃 (R1·R1-b 처치)

단일 외부 앵커(v1 설계)를 폐기하고 **난이도·스타일이 다른 앵커 풀**을 게임별로
등록한다. AlphaStar 리그/PSRO(population-based 상대 다양화)의 발상을 고정
래더로 경량화한 것 — 전체 population 학습은 이 예산에서 과하고, 고정 래더 +
홀드아웃 분리로 같은 목적(과적합 방지 + 그래디언트 복원)을 얻는다.

| 등급 | 정의 | 제작 | 용도 |
|---|---|---|---|
| L1 중수 | 기본 heuristic보다 명확히 강하되 L2보다 약한 봇 (예: Sonnet 즉흥 설계 1회, 또는 기존 채택 챔피언의 과거 버전 동결) | Sonnet 1회 설계 후 봉인 | **그래디언트 복원** — 0% 구간에서도 후보 간 우열 측정 |
| L2 고수 | 기존 Opus봇 (`src/reference/experiments/<gameId>-opus-bot.ts`, ADR-0010으로 이미 고정) | 기존 소스 그대로 앵커 등록 | 피드백 루프의 주 손실 함수 |
| L3 고수2 (홀드아웃) | **새 스타일** Opus 재설계 — L2와 다른 전략 철학을 프롬프트로 강제(예: L2가 위협 중심이면 L3는 territory/포지셔널 중심), 설계 시 L2 소스·LossReport 미제공 | Opus 1회 설계 후 봉인 | **초월 판정 전용.** 설계 피드백(브리프·LossReport·프로브 은행)에 절대 사용 금지 |

- `BenchmarkAnchor`에 `kind: 'external'` + `role: 'feedback' | 'holdout'` 추가.
  홀드아웃 앵커의 trajectory/LossReport 생성은 코드 수준에서 거부한다(시드 뱅크
  홀드아웃 재사용 금지 규칙의 **상대(opponent) 버전** — 같은 원칙의 대칭 적용).
- `WaveConfig.challenge?: { anchorIds, blocks }` — 웨이브 말미에 후보·신규
  합성봇 vs 피드백 앵커들(L1·L2)을 계측해 `WaveReport.challengeResult`에 기록.
  **채택 판정에는 불개입**(과적합 방지 + comparabilityKey 오염 방지 + 기존 채택
  이력과의 판정 일관성). 이 수치가 큰루프의 손실 함수가 된다.
- **초월 판정**은 L3 홀드아웃 앵커 상대 승률로만 한다(§5 Phase 4). L2를 이기고
  L3에 지면 "L2 공략 과적합"이 실측으로 드러난다 — 이것이 이 구조의 존재 이유다.
- 구현 시 **ADR-0012**로 기록.

### D4. 패배 데이터 3단 활용 — 아카이브 → LossReport → 프로브 국면 은행 (R2 처치)

결정론 파이프라인이라 `(seed, botSeeds, seats, choices[])`만 저장하면 전판이
바이트 단위로 재현된다 — **아카이브는 가볍게, 분석은 재생으로**. 이 사실이
아래 3단 전부의 비용을 지배적으로 낮춘다.

**1단 — TrajectoryArchive**: `runHeadToHead`에 `recordTrajectories?: { dir,
maxGames }` 옵션(미지정 시 기존 동작·시그니처 불변). 각 판을
`{seed, botSeedBase, seats, choices: string[](encodeChoice 열), outcome}` JSONL로
저장(`runs/<gameId>/challenge/<id>/trajectories.jsonl`).

**2단 — LossReport** (`loop/loss-mining.ts`, 게임 중립): 후보 패배 판을 재생하며
(a) 패배 확정 깊이 분포(몇 수째부터 결과가 뒤집히지 않는가 — 재생 중 후보 수를
앵커 수로 치환해 보는 counterfactual 프로브), (b) **분기점 대조**: 같은 국면을
앵커 봇에게 질의해 "후보의 선택 ≠ 앵커의 선택"인 지점 추출, (c) 결정지점
(DecisionPointSpec)별 불일치율 집계. encodeChoice/applyChoice/decide만 쓰므로
게임 지식 불요.

**3단 — ProbePositionBank** (핵심 신설): LossReport의 분기점 국면 중 결과
민감도가 높은 것 N개(수십~수백)를 `(seed, choicePrefix)` 형태로 **봉인된 고정
프로브 세트**로 승격한다 — 체스 엔진 개발의 테스트 스위트(EPD/STS) 방식.
효과 두 가지:

1. **초저비용 후보 필터**: 새 후보를 풀 게임 없이 국면 단위로 채점(프로브
   국면에서 앵커 선택과의 일치율 + 즉패 수 회피율). 판당 수백 ms인 게임에서
   국면당 수 ms — screen(행동 지문)과 smoke(SPRT) 사이의 새 저비용 단계가 되어
   **후보 배치 확대(D5)를 처리량 면에서 정당화**한다.
2. **회귀 자산**: 한번 발견된 "지는 국면"이 프로브로 영구 봉인되므로, 이후
   어떤 후보도 같은 함정을 무증거로 통과할 수 없다(패배가 누적 자산이 되는
   구조 — 지금은 패배가 휘발된다).

**주입 경로의 우선순위(중요)**: 패배 데이터의 1차 용도는 ① 프로브 필터,
② 설계 브리프 증거이고, "앵커 행동을 정책에 직접 주입(모방)"은 포트폴리오
(D5)의 한 버킷으로만 둔다 — 이 저장소는 "강자 흉내 정책"이 원본보다 약해지는
현상을 이미 두 번 실측했다(도미니언 챔피언 롤아웃 0.275→0.100 악화, 장기 합성
롤아웃 0.375→0.158 악화). 모방은 시도 가치가 있는 한 축이지 기본 경로가 아니다.

### D5. 포트폴리오 후보 생성 — 큰루프 설계 단계의 다관점화 (R4 처치)

라운드당 후보 배치를 단일 아이디어 직렬 시도에서 **버킷별 비중 배분**으로
바꾼다. 초기 비중(첫 라운드 프리셋):

| 버킷 | 내용 | 생성 주체·비용 | 초기 비중 |
|---|---|---|---|
| B1 활용(exploit) | 챔피언·near-miss의 파라미터 변형(예산·uctC·priorWeight 스윕, 플래그 재조합) | **기계 생성(LLM 0)** | 25% |
| B2 상대 정보(opponent-informed) | LossReport·프로브 불일치 상위 결정지점을 겨냥한 설계 | Sonnet | 25% |
| B3 심층 설계 | 설계 브리프 전체를 읽고 집중 설계 1~2개(자연어 명세+의사코드+예상 반박 → Sonnet 구현) | **Opus** | 15% |
| B4 신규 탐험(explore) | 축 매트릭스(D6) 미시도 축 + 행동 지문이 챔피언과 최대 거리인 후보 우대 | Sonnet(+기계 변형) | 25% |
| B5 모방·이식 | 앵커 행동 클로닝, 타 게임 성공 패턴 이식(예: 윙스팬 IS-MCTS 구성) | Sonnet | 10% |

- **비중은 고정 상수가 아니다**: 라운드마다 버킷별 수율(채택률 + challenge 승률
  Δ 기여)로 재배분하되 각 버킷 하한 5%(탐험 소멸 방지) — 고정 임계의 부당함은
  P6에서 이미 실측으로 증명된 이 저장소의 교훈이고, DESIGN §7의 Optuna 참조
  (탐색-활용 예산 배분)를 실제로 가동하는 것이다.
- **배치 크기 M도 처리량 실측에서 파생한다**(§4 검토 2 참고): M =
  라운드 시간 예산 ÷ (프로브 필터 통과율 × 후보당 웨이브 비용)의 보수적 추정.
  프로브 필터(D4-3단) 도입 전 초기 라운드는 M=8~12, 필터 가동 후 확대.
- **모델 라우팅으로 비용 통제**: B1은 LLM 호출 0, B2·B4·B5는 Sonnet, B3만
  Opus — "Opus급 설계 품질"과 "많은 후보"를 동시에 요구해도 비용이 선형
  폭발하지 않는 구조. 구현 시 **ADR-0013**(포트폴리오 프로토콜)으로 기록.

### D5.5. 큰루프 프로토콜 v2 (DESIGN §6.1 개정안)

1. **웨이브 + challenge 계측**(D3) — 내부 게이트 판정 + 피드백 앵커(L1·L2)
   승률을 한 리포트로.
2. **패배 채굴**(D4) — near-miss 구조화(기존 H10) + LossReport + 프로브 은행
   갱신(신규 분기점 국면 추가 봉인).
3. **설계 브리프 자동 생성**(`artifacts/design-brief.ts`): GameProfile + 축
   매트릭스 현황 + 카드 이력(AdoptionLedger) + LossReport 요약 + 프로브 통계를
   한 마크다운으로 조립. LossReport 유무를 머리에 명시(근거 수준 표시).
4. **포트폴리오 발주**(D5): 버킷별 비중에 따라 후보 배치 생성 — B3만 Opus,
   나머지는 Sonnet/기계.
5. **프로브 필터 → 웨이브**: 프로브 채점으로 배치를 상위 k로 압축한 뒤 정규
   게이트(신규 시드 뱅크) 진입. 채택 판정은 기존과 완전 동일(특례 없음).
6. **비중 재배분 → 1로 복귀.** 종료 조건은 "축 매트릭스 소진 + challenge 승률
   정체 3라운드"이지 라운드 수 상한이 아니다.

ADR-0009(억지 반복 금지)는 유지하되 적용 단위를 명확화한다: 금지되는 것은
"같은 축의 파라미터만 바꾼 **수동 재시도**"이고, B1 버킷의 기계적 스윕은
포트폴리오가 수율로 자동 축소하므로 모순되지 않는다(수율이 낮으면 비중이
스스로 줄어든다 — 사람이 억지로 반복하는 것과 구조가 다르다).

## 4. 사용자 제안에 대한 냉정 검토 (수용/조정 근거)

**제안 1 — 패배 데이터 정밀 기록·정책 주입 (수용 + 방향 조정)**: "기록"은
전면 수용을 넘어 프로브 은행으로 강화했다(패배가 휘발 자산에서 누적 회귀
자산으로). 단 "정책에 직접 주입"을 기본 경로로 삼는 것은 반대한다 — 이
저장소의 실측이 두 번(도미니언 0.275→0.100, 장기 0.375→0.158) "강자 흉내
정책은 원본보다 약하다"를 보여줬다. 모방은 B5 버킷(10%)으로 시도하되, 주
활용 경로는 ① 프로브 필터(선별 신호), ② 브리프 증거(설계 입력), ③
counterfactual 분기점 대조(원인 규명)다.

**제안 2 — 중수/고수/신스타일 고수2 래더 (전면 수용 + 원칙 정합화)**: 제안
그대로가 연구 표준(AlphaStar 리그의 main/exploiter 구분, PSRO의 상대 다양화)과
일치하고, 이 저장소에 이미 있는 원칙과도 정합된다 — L3 홀드아웃 앵커는 **시드
뱅크 홀드아웃 규칙의 상대 버전**이다. 추가 발견: 중수 앵커의 진짜 가치는
과적합 방지보다 **그래디언트 복원**이다(현 오목 진단은 전부 0%라 손실 함수가
무정보 — L1 상대 승률 곡선이 있어야 카드 간 우열이 측정된다). 더 무거운
대안(전체 population 학습, 온라인 exploiter 생성)은 이 예산(맥북, 동시 1개)에서
기각 — 고정 래더 + 홀드아웃 분리가 같은 목적의 최소 구현이다.

**제안 3 — 100개 후보의 비중 분할 포트폴리오 (방향 수용, 숫자 조정)**: 다관점
비중 배분은 R4의 정확한 처치라 수용한다(B1~B5). 단 두 가지를 조정한다:
① **100개/라운드는 현 예산에서 불가** — 오목 s256 웨이브가 티어당 수십 블록
× 수백 ms/판이고 무거운 연산 동시 1개 규칙(GAP-8 §4 자원 사고) 아래에서
100후보 × 다단 게이트는 며칠 단위가 된다. 대신 프로브 필터(D4-3단)라는 초저비용
선별 단계를 만들어 "많이 생성하고 싸게 거른 뒤 소수만 웨이브에 태우는" 구조로
같은 목적을 달성한다 — 배치 크기는 고정 상수가 아니라 처리량 실측에서
파생한다(P6 교훈의 일관 적용). ② **비중 고정%도 두지 않는다** — 초기 프리셋만
두고 버킷별 수율로 재배분(하한 5%). "10%, 30%, 25%"라는 특정 숫자보다 "비중이
데이터로 조정되는 구조"가 제안의 본질이라고 판단했다.

## 5. 실행 계획 — Opus·Sonnet만으로 진행 가능한 단계별 작업 지시

역할 규약: **설계·판단·브리프 해석·B3 버킷 = Opus** / **코드 구현·테스트·측정
실행·B2/B4/B5 버킷 = Sonnet** / **B1 버킷 = 기계 생성(LLM 불요)**. 각 Phase는
독립 커밋 단위이고, 커밋 전 `npm run typecheck` + `npm test` 필수. 무거운
측정은 동시 1개·`nice -n 10`·힙 오버라이드 금지(GAP-8 §4 규칙).

### Phase 1 — 패배 인프라 + 앵커 래더 (D3+D4) [예상 1.5일]

이후 모든 실험의 계측 기반이므로 최우선(사용자 지시의 우선순위이기도 하다).

1. [Sonnet] `runHeadToHead` trajectory 기록 옵션 + `loop/loss-mining.ts`
   (LossReport: 패배 확정 깊이·분기점 대조·결정지점별 불일치율) + 단위테스트
   (소형 픽스처로 분기점 대조 검증).
2. [Sonnet] `BenchmarkAnchor`에 `kind:'external'`+`role:'feedback'|'holdout'`,
   홀드아웃 앵커의 LossReport 생성 거부 가드 + 테스트. ADR-0012 작성.
3. [Sonnet] 오목·도미니언·하스스톤 L2 앵커 등록(기존 Opus봇 소스 그대로 봉인).
4. [Sonnet 설계+구현] L1 중수 앵커 3게임(1회 즉흥 설계 후 봉인 — 기준:
   heuristic에 유의하게 이기고 L2에 유의하게 지는 것을 등록 전 실측 확인).
5. [Opus 설계, Sonnet 구현] L3 고수2 앵커 3게임 — L2와 다른 전략 철학 강제,
   설계 시 L2 소스·패배 데이터 미제공. 등록 즉시 봉인, 이후 피드백 경로 차단.
6. [Sonnet] `loop/probe-bank.ts` — LossReport 분기점 → 프로브 국면 봉인 +
   후보 프로브 채점기. **판정 실험**: 오목 v5 vs L2 N=100 기록 → LossReport →
   프로브 은행 초기화. "패배 평균 확정 깊이·최다 불일치 결정지점"이 수치로
   나오고, L1 상대 승률이 0%가 아니면(그래디언트 복원 확인) 성공.

### Phase 2 — 트리 prior (D1+D2) [예상 1일]

1. [Sonnet] `contract/types.ts`에 `choiceEvaluator?` 추가(하위호환) + ADR-0011.
2. [Sonnet] `search/mcts.ts` priorWeight/progressive bias — 회귀 핀: 미지정 시
   기존 30시드 trajectory 지문 완전 일치(P2 검증법 재사용).
3. [Sonnet] 오목 어댑터 choiceEvaluator(forkAwareness 위협 스코어링 재표현).
4. **판정 실험**: `mcts4-s256-prior`(priorWeight 스윕 3점) 진단 — 이제 래더
   전체(L1·L2)로 측정한다. 성공 기준: L2 상대 9.0%(순정 forkAwareness) 초과
   또는 L1 상대 승률 곡선에서 유의한 단조 개선. 0% 무정보 문제는 Phase 1이
   이미 해소한 상태라, 실패해도 priorWeight-승률 곡선이 브리프 입력이 된다.

### Phase 3 — 포트폴리오 프로토콜 v2 (D5+D5.5+D6) [예상 1.5~2일]

1. [Sonnet] `artifacts/design-brief.ts`(브리프 조립) + 버킷 정의·수율 추적

**알아둘 주의점(감추지 않는다)**: ① 도미니언 L3(74.8%)는 L1(100%)보다 heuristic
상대 승률이 낮다 — 홀드아웃 자격 요건은 충족하나 "고수2"라는 이름과 실제
강도의 간극 가능성이 있다. 앵커 봉인 규칙상 교체하지 않으며, 초월 판정에서
L3가 너무 쉽게 뚫린다고 판단되면 별도 anchorId(`external-style2b-l3`)로 보강
등록한다(갱신이 아닌 신규 등록이라 규칙 정합). ② 오목 L3-L2 지문 일치율
69.2%는 기준(0.7)에 마진 0.8%p로 근접 — 오목의 즉승/즉방어 안전망이 두 봇에서
공유되는 구조적 겹침 때문으로, 스타일 차이는 중반 운영에 있다.

## 6. 리스크와 한계 (감추지 않는다)

- **오목은 prior로도 안 될 수 있다.** 카드 5장의 실측이 가리키는 대안 가설:
  256-sim 예산 자체가 15×15 오목의 전술 지평선에 근본 부족. Phase 2가 실패해도
  L1 승률 곡선·priorWeight 곡선이 "예산 스케일업 결정"의 근거 데이터가 된다.
- **L1·L3 앵커의 품질 리스크**: L1이 너무 약하면 그래디언트 복원 실패, L3가
  L2와 사실상 같은 스타일이면 홀드아웃이 무의미. 등록 전 실측 게이트(L1:
  heuristic<L1<L2 확인, L3: L2와의 행동 지문 거리 + 상호 대전 비이행성 확인)를
  통과해야 봉인한다.
- **프로브 은행 과적합**: 프로브 일치율은 선별 신호이지 채택 근거가 아니다 —
  채택은 여전히 신규 시드 뱅크의 다단 게이트만으로 한다(프로브는 웨이브 진입
  전 압축 단계에만 관여). 프로브 국면이 특정 앵커에서만 나왔다는 출처를
  레코드에 명시한다.
- **포트폴리오 오버헤드**: 버킷·수율 관리가 배보다 배꼽이 되지 않도록 v1은
  마크다운+JSON 기록 수준으로 시작한다(자동 스케줄러는 수율 데이터가 3라운드
  쌓인 뒤 판단).
