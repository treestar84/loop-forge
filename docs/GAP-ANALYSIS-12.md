# 갭 분석 12 — 루프포지 자체의 고도화: 인프라 성숙도 검토 (2026-07-30/31)

> GAP-11이 "왜 특정 게임이 챗봇 AI를 못 이기는가"(게임 전략 문제)를 다뤘다면,
> 이 문서는 "그 처치를 실행하는 장치 자체가 얼마나 지속 가능한가"(프레임워크
> 문제)를 다룬다. 사용자 지시: "루프 포지 자체를 고도화하는 부분에 있어서
> 검토를 해달라." 근거는 코드베이스 실측 조사(§0)이며, 추측이 아니라 수치다.

## 0. 실측 조사 결과 (조사 전용 에이전트, 코드 무수정)

### 0.1 라운드 러너 파일 — diff가 파일 전체 크기를 초과

| 비교 | 앞 파일 | 뒤 파일 | diff 줄 수 |
|---|---|---|---|
| 오목 1→2회전 포트폴리오 | 444줄 | 548줄 | **507줄** |
| 도미니언 1→2회전 포트폴리오 | 493줄 | 582줄 | **657줄** |
| 도미니언 2→3회전 포트폴리오 | 582줄 | 726줄 | **641줄** |
| 오목 1→4회전 채굴 | 312줄 | 363줄 | 317줄 |

**diff가 원본 파일 크기와 맞먹거나 넘는다** — 이건 "다른 부분만 고친
변형"이 아니라 사실상 매번 처음부터 다시 쓴 것과 같다. `src/reference/
runners/shared/`에 12개 공유 파일이 있지만 전부 전략 플래그
정의(`*-mcts-flag.ts`)나 후보 목록(`gomoku-round{1..4}-candidates.ts`)뿐 —
**라운드 실행 흐름 자체(시드 예약 → 프로브 필터 → 웨이브 → challenge →
승격 → 재배분 → JSON 저장)는 공유화된 적이 없다.**

### 0.2 프로토콜 심화가 3/9 게임에서 멈춰 있다

| 메커니즘 | 적용 게임 |
|---|---|
| 앵커 래더(L1/L2/L3) | 오목·도미니언·하스스톤(**3개**) |
| `choiceEvaluator` | 오목·도미니언·하스스톤(**3개**, 정확히 동일 집합) |
| `priorWeight`/`priorEvaluator`/`priorWeightSchedule` | 오목·도미니언·하스스톤(**3개**, 동일 집합) |
| `portfolio-state.json`(포트폴리오 수율 재배분) | 오목·도미니언·하스스톤(**3개**, 동일 집합) |

스플랜더·윙스팬·장기·아발론·카탄·mini-trick **6개 게임은 GAP-11 이전
상태(2026-07-28 이전 벤치마크)에 그대로 멈춰 있다.** 이건 우연이 아니라
"내가 어느 게임에 손을 댔는가"의 결과다 — 프레임워크 기능이 아니라
사람(에이전트)이 매번 손으로 적용한 일회성 작업이었다는 뜻이다.

### 0.3 재배분 값은 실제로 읽히지만, 그걸 담는 그릇은 매번 다시 만든다

`reallocate()`/`loadPortfolioState()`는 7개 라운드 파일에서 실제로
호출되고 다음 라운드에 반영된다(설계대로 작동 — 하드코딩 아님). 하지만
**그 호출을 감싸는 300~500줄가량의 티어 반복 로직(screen→smoke→prune→
holdout→regression 5단계, `withStrategyFlags` 확장 3회 등)은 매 라운드
파일에 인라인으로 새로 쓰였다**(§0.1 diff가 그 증거). 포트폴리오 "데이터"는
파이프라인화됐지만 포트폴리오 "실행"은 파이프라인화되지 않았다.

### 0.4 테스트 스위트가 세션 중 4.2배 느려졌다

12.8초 → 54.1초, 전부 `compose.test.ts` 한 파일(53.4초)에 집중. Phase 3에서
30초→5초로 한 번 조정했으나(시드 30→5→3), 이후 회귀 테스트가 더 늘면서
다시 누적된 것으로 보인다 — **속도 회귀를 잡는 절차가 일회성 대응이었지
지속적 예산(budget) 개념이 아니었다.**

### 0.5 문서가 append-only 로그가 되고 있다

`GAP-ANALYSIS-11.md`가 이번 세션 한 번에 384줄→655줄(+70%)로 늘었다.
라운드가 끝날 때마다 §5.5에 한 단락씩 계속 추가하는 구조라, 지금은
"이 게임이 왜 안 되는지 이해하려면 655줄을 순서대로 읽어야 하는" 상태다.
"무수히 반복한다"는 이 프로젝트의 목표를 문자 그대로 따르면 이 파일은
10라운드 뒤 2,000줄을 넘는다.

### 0.6 `search/mcts.ts`·`ismcts.ts`가 옵션 필드의 누적 지점이 되고 있다

파일 개수는 그대로인데 줄 수만 +40%. `rolloutPolicy`·`rolloutFactory`·
`tacticalDepth`·`tacticalBranchCap`·`rootOverride`·`priorWeight`·
`priorSource`·`priorEvaluator`·`priorWeightSchedule` — 9개의 독립 옵션
필드가 같은 두 파일, 같은 핵심 함수(`selectChild`/`runMcts`)에 전부
누적됐다. 각각은 "미지정 시 불변"을 지켜 개별로는 안전하지만, **9개
옵션의 조합 공간(2^9 근사)에 대한 상호작용 테스트는 존재하지 않는다** —
이번 세션에 실제로 5개(rolloutFactory+priorEvaluator+priorWeightSchedule+
tacticalDepth 등)를 동시에 쓴 후보가 있었는데, 그 조합 자체의 정확성은
"미지정 시 불변" 회귀 핀만으로는 검증되지 않는다.

## 1. 근본 원인 — 왜 이렇게 됐는가

### F1. "라운드 실행기"라는 추상화가 존재한 적이 없다

DESIGN §6.2가 6단계 프로토콜을 문서로는 정의했지만, 그걸 실행하는 코드는
매 라운드 Sonnet 에이전트가 선례 파일을 참고해 손으로 새로 쓰는 방식이었다
(이번 세션의 모든 위임 프롬프트가 "선례: `<이전 라운드 파일>`(구조)"라고
지시한 것 자체가 증거). 이건 데이터 재사용(포트폴리오 상태, 프로브 은행)은
됐지만 **제어 흐름 재사용은 안 된 상태**다.

### F2. 심화 메커니즘 도입이 "프레임워크 기능 추가"가 아니라 "그 게임에
대한 일회성 작업"으로 취급됐다

앵커 래더·choiceEvaluator·포트폴리오는 전부 옵트인 계약 필드로 설계돼
있어(정확한 설계 원칙) 어떤 게임에도 적용 가능하지만, 실제로 "이 6게임에도
적용하라"는 지시나 자동화 트리거가 없었다 — 사람이 시킨 3게임에만
적용됐다. 확장 가능한 설계와 실제 확장은 다른 문제다.

### F3. 비용(테스트 시간·문서 길이)에 대한 예산 개념이 없다

각 안전장치(회귀 다이제스트 테스트, 라운드 로그 추가)는 그 자체로는
합리적인 결정이었지만, "테스트 스위트는 X초 이내" "문서는 Y줄 이내, 넘으면
분할" 같은 상한이 없어 매 결정이 지역적으로는 옳고 전체적으로는 누적
비용이 된다.

### F4. 옵션 필드 누적이 계약 설계 원칙과 충돌하기 시작했다

"미지정 시 불변"은 개별 필드의 안전을 보장하지만, 여러 필드가 **동시에
지정된 조합**의 정확성은 아무것도 보장하지 않는다. 지금까지는 운 좋게
문제가 안 됐지만(각 조합이 순차적으로 파이프라인처럼 적용되는 구조라
상호작용이 제한적) 필드 수가 늘수록 이 가정이 깨질 위험도 커진다.

## 2. 고도화 제안 (우선순위순, 각각 D1~D5로 명명 — GAP-11의 D-넘버링과
구분하기 위해 이 문서 안에서는 E1~E5로 표기)

### E1(최우선) — 라운드 실행기를 실제 코드로 추출

`src/reference/runners/shared/round-executor.ts`(가칭) 하나를 만들어
DESIGN §6.2의 5단계(프로브 필터→웨이브→challenge→승격→재배분)를 함수로
캡슐화한다:

```ts
export async function runPortfolioRound(config: {
  adapter, probeBanks, candidates, waveSeedBase, challengeSeedBase,
  regressionOpponentFlags, portfolioStatePath, outputPath,
}): Promise<PortfolioRoundReport>
```

게임별 라운드 파일은 이 함수 호출 + 후보 목록(게임 지식)만 남는다 —
diff가 파일 크기를 초과하는 일이 구조적으로 불가능해진다(공유 로직을
고치면 한 곳만 고치면 된다). **이건 이번 조사에서 발견된 가장 크고 가장
명확한 부채이고, 다음 라운드부터 바로 효과가 난다.**

### E2 — 6개 미적용 게임에 "최소 GAP-11 적용" 일괄 라운드

스플랜더·윙스팬·장기·아발론·카탄·mini-trick에 앵커 래더(L1/L2/L3 등록)만
이라도 먼저 깐다 — challenge 계측이 없으면 이 6게임은 여전히 "무정보"
상태이고, GAP-11의 핵심 처치(외부 강자를 손실 함수로 편입)가 적용 안 된
채로 남는다. E1(라운드 실행기)이 먼저 있으면 이 확산 비용이 훨씬 낮아진다
— 순서상 E1 다음이 맞다.

### E3 — 문서 분할: "라운드 로그"와 "살아있는 진단"을 분리

`GAP-ANALYSIS-11.md`를 두 파일로 쪼갠다: ① §0~§4(원인 진단·처치 설계,
안 바뀌는 부분)는 그대로 두고 ② §5.5(라운드별 실행 기록, 계속 느는 부분)는
`docs/GAP-11-ROUNDS.md`(또는 게임별 `runs/<gameId>/summary.md`를
`renderGameSummaryMarkdown`로 이미 만들고 있으니 그걸 라운드 로그의 정본으로
승격)로 옮긴다. 새 라운드가 끝나면 진단 파일이 아니라 로그 파일에 추가한다.

### E4 — 테스트 시간에 명시적 예산 도입

`npm test`가 지금 54초 — 이 저장소가 이전에 유지했던 "빠른 피드백 루프"
관행(12.8초)과 다시 얼마나 멀어졌는지 라운드마다 확인하는 절차가 없다.
CLAUDE.md 또는 TROUBLESHOOTING.md에 "무거운 회귀 테스트를 추가하기 전에
전체 스위트 시간을 재고, 30초를 넘기면 시드 수·범위를 줄여서 맞춘다"는
명시적 상한을 성문화한다(이미 한 번 처치했던 패턴을 규칙으로 승격).

### E5 — 옵션 필드 조합 계약을 명시화

`MctsConfig`의 9개 옵션 필드 중 실제로 동시 사용 가능한 조합과 우선순위
(`rootOverride > tacticalDepth > 일반 MCTS(prior 포함) > rollout`처럼 이미
암묵적으로 존재하는 순서)를 doc comment 한 곳에 표로 정리하고, 조합
테스트(예: rolloutFactory+priorEvaluator+tacticalDepth 3종 동시 지정 시
결정론·우선순위 확인)를 최소 1건 추가한다. 급하지 않지만 필드가 하나 더
늘기 전에 해두는 게 싸다.

## 3. 우선순위와 이유

E1(라운드 실행기)이 압도적 1순위다 — 나머지(E2~E5) 전부 E1이 있으면 비용이
낮아지거나(E2), E1과 함께 자연스럽게 해결되거나(E4, 실행기 안에 티어별
seed 검증을 표준화하면 무거운 세션이 반복 발생할 여지가 줄어듦), 독립적으로
언제 해도 되는 성격(E3, E5)이다.

**이번 문서는 검토이지 실행 지시가 아니다** — 다음 단계로 진행할지, 어떤
항목부터 할지는 사용자 결정이 필요하다.

## 4. E1 실행 기록 (2026-07-30, 완료)

`src/artifacts/portfolio-round.ts`의 `runPortfolioRound()`로 5단계(프로브
필터→웨이브→challenge→assembleFlags 승격→bucketOutcomes/reallocate→저장)
추출 완료. **새 알고리즘 없이 기존 오목 round4·도미니언 round3 로직을
그대로 옮긴 것** — 안전장치로 리팩터 전후 같은 시드로 재실행해 필드별
완전 일치를 확인했다(도미니언은 `assembleFlags`의 `excluded` 배제 문구까지
동일 — GAP-11-ROUNDS.md의 첫 실전 승격 사례가 그대로 재현됨).

부수 효과: 테스트 스위트가 오히려 개선됐다(54초대→46.7초) — §0.4가 지적한
문제를 이 작업이 악화시키지 않았음을 확인. 이탈(명세 보완) 5건: 비용 체크·
challenge용 상대 봇/시드베이스 필드, `waveId`(부트스트랩 재샘플 시드 파생
보존을 위해 문자열 그대로 전달 필수), `recordedAt`/`clockNowMs`(artifacts
계층의 결정론 규칙 준수를 위해 앱 경계에서 주입), 결과 인터페이스에
`criteria`(near-miss 추출용) 추가 — 전부 명세가 놓친 실행상 필수 파라미터.

오목 round1~3·도미니언 round1~2는 손대지 않음(과거 실행 기록 보존).
**다음 라운드(도미니언 4회전 등)부터 새 후보 배치만으로 이 실행기를 쓸 수
있다** — §0.1의 "diff가 파일 크기를 초과" 문제가 구조적으로 재발 불가능.

## 6. E4 실행 기록 (2026-07-31, 완료)

`docs/TROUBLESHOOTING.md` §12로 성문화: 무거운 회귀 테스트 추가 전
① 현재 `npm test` 시간 확인 ② 그 테스트가 통계적 검증인지 결정론적 동일성
검증인지 구분(후자는 시드 수를 줄여도 신뢰도 손실 없음) ③ 추가 후 시간이

## 7. E2 v2 — 재구간화 (2026-07-31, 사용자 지시 "실험 횟수 부족" 진단에 따른 재설계)

E2가 §2에서 "6게임 일괄 최소 적용"으로 제안됐다가 사용자 검토에서 "이 항목은
의심여지없이 적합한 구현권장 항목인거지?"라는 질문에 냉정하게 재검토한 결과
보류됐다(FIX-BACKLOG.md, 사유: 6게임이 실제로는 서로 다른 상태의 세 그룹이라
일괄 처치가 부적합). 지금 다시 열어 그룹별로 재설계한다 — 목표는 "루프포지가
챗봇 AI를 이겼다"는 증거 표본을 3게임(오목·도미니언·하스스톤)에서 늘리는 것.

### 그룹 A — 스플랜더·윙스팬 (GAP-11 정규 편입, 우선순위 높음)

두 게임 다 옛 3열 벤치마크 방법론으로는 이미 Opus봇을 이겼다(스플랜더 C열
Opus 승률 6.9%, 윙스팬 76.9%→24.3% 역전). 하지만 **GAP-11 인프라(외부 L2
앵커 등록·loss-mining·portfolio-round)가 전혀 없다** —
`hearthstone-anchor-ladder.ts` 같은 파일이 두 게임에 존재하지 않는 것으로
확인(오목·도미니언·하스스톤 3게임에만 있음). E1(portfolio-round.ts)이 이미
게임 중립으로 추출돼 있어 이 두 게임에 배선하는 비용은 낮다 — Phase 1(L1/L2/L3
앵커 등록, 기존 `*-opus-bot.ts`를 L2 소스로 그대로 봉인)부터 순서대로 GAP-11
Phase 1~3을 적용하면 "3게임→5게임"으로 정규 표본이 늘어난다. 옛 벤치마크가
이미 승리를 보였으므로 L2 앵커 상대로도 빠르게 유의한 결과가 나올 가능성이
높다 — 비용 대비 증거 확장 효율이 가장 좋은 트랙.

### 그룹 B — 장기·아발론·카탄 (GAP-11 적용 전에 "첫 채택"부터 필요)

세 게임 전부 **어떤 방법론으로도 채택 후보가 0개**다 — 이건 "외부 강자
비교가 없다"는 GAP-11의 문제가 아니라 그 이전 단계, "이 게임에서 이기는
전략을 아직 하나도 못 찾았다"는 더 근본적인 문제다. GAP-11의 prior 주입·
loss-mining은 "이미 있는 챔피언을 외부 강자 상대로 더 강하게" 만드는
장치이지 "첫 채택"을 대신 만들어주지 않는다. 게임별 병목이 다르므로 각각
다른 첫 카드가 필요:

| 게임 | 기존 진단 | 다음 카드(A8 도메인 재설계, 전부 미시도) |
|---|---|---|
| 장기 | `mcts-s16` smoke 0.000(O6) — 처리량 제약으로 탐색이 사실상 무력, 축 매트릭스도 "탐색 예산 대비 휴리스틱이 강한 게임"으로 기록 | 탐색 확대가 아니라 휴리스틱 자체 개선(기물 안전도·기동성 가중치 재설계)을 첫 카드로 — 예산 축은 이미 소진(ADR-0009) |
| 아발론 | 숨은 진영 게임이라 승리조건 자체가 비대칭 — 온보딩 채점 시스템의 기본 가정과 충돌했던 걸 `hiddenTeamStructure`로 고친 뒤에도 전략 후보 설계 자체는 아직 시도된 적 없음(축 매트릭스에 아발론 행 자체가 없음) | 투표 이력 기반 베이지안 의심도 추적(다른 플레이어의 과거 투표 패턴으로 진영 추정 갱신) — 은닉정보 게임 전용 A8 |
| 카탄 | FFA/킹메이킹, "채택 후보=상대 동일봇일 때 좌석 순열 평균이 정확히 1/4로 수렴"이 수학적으로 검증됐을 뿐 실제 전략 후보 설계 자체는 미시도 | 자원 희소성 가중 거래 평가(부족한 자원일수록 거래 수용 임계 상향) — FFA 전용 A8 |

이 트랙은 Opus 수준의 게임별 도메인 분석이 필요해 그룹 A보다 비용이 높다.
