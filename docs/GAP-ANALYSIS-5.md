# 갭 분석 5차 — 목표 정합성 점검 (v1.4 시점)

> 방법: 특정 게임이나 메커니즘 계열이 아니라, 프로젝트의 **두 궁극 목표**에 실제
> 코드/문서가 얼마나 부합하는지를 3개 탐색 에이전트로 전수조사했다. 지금까지
> (1~4차)의 갭은 "온보딩이 되느냐"에 집중했고, 이번은 "온보딩 이후 운용 단계에서
> 여러 게임을 반복적으로 다룰 때 무엇이 무너지는가"를 봤다.
>
> **목표 1**: 사용자가 보드게임류 프로젝트를 그대로 전달 → 온보딩 점수 검증 요청 →
> 점수가 낮으면 구현을 더 해서 완성도를 높임 → 통과하면 온보딩 1차 완료.
>
> **목표 2**: 온보딩된 프로젝트가 큰루프/작은루프/벤치마크의 반복 루프를 돌며 봇
> 난이도 상승 전략을 발굴 → 사용자는 명확한 형태의 산출물을 받음 → 큰루프에는
> 사용자가 어느정도 개입 가능.

---

## 목표 1 관련 발견

### H1. 채점 리포트가 "게임 규칙 언어"가 아니라 "어댑터 API 언어"로 쓰여 있다 [높음, 신규]

`scoreAdapter`의 `remediation` 문자열은 `getObservation`, `applyChoice`,
`mutateHidden`, `seatingPlan`, `choiceKeys/encodeChoice` 같은 **Loop Forge 내부
계약 용어**를 그대로 쓴다(`score.ts` C0~C7 전수 확인). 로프-포지 내부를 모르는
게임 개발자가 "내 게임의 어떤 규칙이 문제인지"로 즉시 번역할 수 있는 문구는
`C2_DEFECTS`의 max-decisions 특수 케이스(§C2, "게임의 종국 보장 규칙 미구현 여부를
확인하라") **단 하나뿐**이다. 나머지(`C3_PROBE_NEVER_MUTATED`, `C6_ALL_NOOP`,
`C7_FIXTURE_MISMATCH` 등)는 어댑터 함수명을 대라고만 한다. `renderReportMarkdown`
자체도 축 코드가 뭘 검사하는지 설명하는 서문·용어집이 없다.

목표 1의 "점수가 낮으면 구현을 더 해서 완성도를 높인다"는 흐름이 성립하려면, 리포트를
읽는 사람(사람이든 에이전트든)이 "이 blocker → 원본 게임의 이 규칙이 빠졌다/틀렸다"로
번역할 수 있어야 한다. 지금은 그 번역이 전적으로 리포트를 읽는 쪽의 암묵지에
의존한다.

- **처치**: `docs/`에 defect-code → 게임 규칙 언어 매핑표(예: `DEFECT-GLOSSARY.md`)를
  만들거나, `score.ts`의 각 `remediation`에 "이건 보통 당신의 게임에서 X가 빠졌을 때
  발생합니다" 문장을 한 줄씩 추가. 후자가 리포트 하나로 완결되니 더 낫다.

### H2. `docs/ONBOARDING-GUIDE.md` §3(G-Score 반복 루프)이 4줄짜리 문단 하나뿐 [중간]

"채점→수정→재채점"이 목표 1의 핵심 반복 루프인데, 가이드에는 실제 워크스루나 예시
없이 한 문단("`scoreAdapter(adapter)` 실행 → blocker/remediation 따라 수정 →
재채점")으로 끝난다. §5~§7(계열별 함정, ~100줄)에 비해 압도적으로 부실하다 — 초기
G-Convert보다 "이미 만들어진 어댑터를 반복 개선하는" 이 루프가 실제로는 목표 1에서
더 자주 반복될 작업인데도 그렇다.

- **처치**: §3을 확장해 실제 리포트 예시(blocker 몇 개 → 수정 diff → 재채점 결과)를
  하나 넣는다. 이번 세션의 오목/스플랜더 Z1/Z2 사례가 좋은 소재다.

### H3. "수정은 어댑터 안에서만, 원본은 안 건드림"과 사용자의 "원본 완성도를 높인다"가
    개념적으로 어긋날 수 있다 [확인 필요, 사용자 응답 대기]

`docs/ONBOARDING-GUIDE.md` §2는 명시적으로 "**원본 프로젝트를 고치는 게 아니라**,
원본의 룰을 참조 구현 삼아 어댑터 안에 headless로 재구성한다"고 못박는다. 즉 현재
설계에서 conformance 점수를 올리는 모든 수정은 **어댑터 코드**(`src/reference/*.ts`)
안에서 일어나지, 사용자가 건네준 원본 게임 저장소 안에서 일어나지 않는다(이번 세션의
스플랜더 Z7 — `takeDone` 합성 액션, `STALE_TURN_LIMIT` 자체 도입 — 이 정확히 이
패턴이었다).

**해소(2026-07-21, 사용자 확인)**: ②(로프-포지 어댑터를 고친다)가 맞다 — 현재 설계와
일치. 원본 게임 저장소는 계속 참조 전용으로 두고, `src/reference/*.ts` 안의 headless
재구현을 개선하는 것이 "완성도를 높인다"의 실체다. 별도 처치 불요, 개념 정렬 문제였을
뿐 설계 변경 없음.

### H4. "프로젝트를 그대로 전달"과 현재 v1의 수작업 온보딩 비용 사이 간극 [기대치 정렬,
    이미 로드맵에 있음]

`ROADMAP.md` v3가 이미 "G-Profile 소스 자동 분석", "self-serve 온보딩(에이전트가
전환 작업 자체를 수행)"을 미착수 항목으로 인정하고 있다. 이번 세션에서 스플랜더/오목
2개를 온보딩하는 데 여러 서브에이전트가 상당한 분량의 코드를 새로 작성해야 했다 —
"그대로 전달하면 끝"이 아니라 "전달 후 상당한 어댑터 구현 작업이 필요"가 v1의 실제
모습이다. 새 갭은 아니고(이미 로드맵에 있음), 목표 1의 문구가 v1 범위인지 v3
범위(완전 자동)인지 기대치를 맞출 필요는 있다.

## 목표 2 관련 발견

### H5. 게임별 실행 진입점 부재가 실측으로 재확인됨 — 여러 게임 운용의 최우선 차단 요소
    [높음, Z3와 동일 갭의 추가 증거]

`dependency-rules.test.ts`의 `layerOf`는 `src/reference/<gameId>/adapter.ts`처럼
하위 디렉토리를 둬도 최상위 세그먼트만 보므로 `reference` 레이어로 정상 인식된다
(여러 게임을 서브디렉토리로 분리하는 데는 문제 없음). 하지만 `APP_BOUNDARY_FILES`/
`DETERMINISM_EXEMPT`는 **`'reference/demo.ts'` 리터럴 하나만** 하드코딩돼 있어,
게임마다 웨이브를 돌리려면 그 게임의 진입점 파일 경로를 이 두 목록에 명시적으로
추가해야 한다. 게임이 늘어날수록 이 목록도 계속 늘어나는 구조 — Z3(이미 백로그에
있음)의 설계 확정이 여러 게임 운용의 실질적 선결 조건임이 이번 조사로 재확인됐다.

### H6. `RunStore`의 `runId`가 게임별로 네임스페이스되지 않는다 [높음, 신규]

`runId`는 호출자가 고르는 자유 문자열이고(`RUN_ID_PATTERN` 경로 안전성만 검사),
`RunStore`는 append-only라 같은 `runId`를 다시 저장하면 throw한다. 두 게임이 같은
`runId`(예: 관례상 다들 `"conformance-report"`라고 지을 수 있음)를 고르면 같은
`rootDir/runs/` 아래서 충돌한다. 지금까지는 `demo.ts`가 게임 이름을 수동으로 접미사에
넣는 관례(`conformance-mini-trick`)로 우연히 피해왔을 뿐, 강제되는 규칙이 아니다.

- **처치**: `RunStore.saveRun`이 `gameId`를 필수 필드로 받아 `runId`를
  `${gameId}/${callerRunId}` 형태로 정규화하거나, 최소한 `runId`에 `gameId` 접두어를
  강제하는 검증을 추가.

### H7. `BaselineRegistry`/`AdoptionLedger`를 세션마다 새로 만들고 재로드하는 관례가
    없다 [중간, 신규]

둘 다 `toJSON`/`fromJSON`을 지원하지만, `demo.ts`는 항상 `new BaselineRegistry()`/
`new AdoptionLedger()`로 새로 시작한다. 같은 게임을 다른 세션에서 두 번째로
온보딩·웨이브 실행하면 이전 앵커·채택 이력을 이어받을 방법이 코드베이스 어디에도
없다 — 매번 임시방편 글루 코드를 짜야 한다. 목표 2의 "체계화된 루프"가 여러 세션에
걸쳐 누적되려면 이게 반드시 필요하다.

- **처치**: 게임별 상태 디렉토리 관례(예: `runs/<gameId>/registry.json`,
  `runs/<gameId>/ledger.json`) + 로드 헬퍼(`loadOrCreateRegistry(gameId)`류)를
  H5(Z3)의 진입점 설계와 함께 정의.

### H8. 5종의 독립 run이 흩어져 있을 뿐, "명확한 형태의 산출물" 하나로 묶이지 않는다
    [중간, 신규]

`conformance-*`, `calibration-*`, `wave-*`, `benchmark-*`, `strategy-history` —
각각 별도 `runs/<runId>/report.md`로 저장되고, 이를 하나로 합치는 대시보드/요약
함수가 `src/artifacts/` 어디에도 없다(`listRuns()`는 인덱스일 뿐 병합이 아님).
사용자가 목표 2에서 기대하는 "명확한 형태의 산출물"이 지금은 "5개 파일을 다 열어
직접 종합해야 하는 상태"다.

- **처치**: `src/artifacts/`에 `renderGameSummaryMarkdown(gameId, runs)`류의
  최종 요약 함수 신설 — 온보딩 점수 한 줄, 채택된 전략 목록, 앵커 사다리 진행도,
  다음 루프 노트를 한 페이지로 압축. RunStore/BaselineRegistry/AdoptionLedger를
  전부 읽어 합성하므로 `artifacts` 레이어에 자연스럽게 위치.

### H9. 큰루프의 "사용자 개입 지점"이 사실상 설계돼 있지 않다 [높음, 신규 — 목표 2의
    핵심 주장과 직결]

`DESIGN.md` §6의 전체 내용은 이 한 문장뿐이다: "WaveReport의 실패 패턴 요약이 다음
후보 설계의 입력 포맷으로 규격화된다(**사람 또는 에이전트가 설계**). 후보 자동
생성은 v2+." 이게 전부다 — 리뷰/승인 워크플로우, 후보 제안 인터페이스, "이 웨이브
결과를 보고 사람이 다음에 뭘 해야 하는가"에 대한 어떤 구체적 절차도 없다.

더 근본적으로: `StrategyFlagSpec`(`apply: (base) => base`)은 **항상 TypeScript
클로저로 작성**해야 하고, config/데이터 기반으로 제안할 방법이 계약에 전혀 없다.
새 후보 전략 하나를 시험해보려면 코드를 새로 짜고 어댑터를 재빌드해야 한다 — 이게
"사용자가 어느정도 개입이 가능함"이라는 목표 2의 표현과 실질적으로 얼마나 부합하는지
재점검이 필요하다. 사용자가 프로그래머라면 문제없지만, 목표 2 문구가 "비개발자도
개입 가능"을 뜻한다면 지금 설계로는 불가능하다.

- **처치**: 최소한 (a) 웨이브 결과를 받아 사람이 검토할 수 있는 표준 산출물(H8과
  연결), (b) 다음 후보를 어떤 형식으로 제안하면 되는지에 대한 명시적 절차 문서화가
  선행돼야 한다. 완전 자동 후보 생성(ROADMAP v2)까지는 안 가더라도, "개입"이 실제로
  뭘 의미하는지부터 설계해야 한다.

### H10. `nextLoopNotes`가 이름과 달리 다음 루프에 실제로 피드백되지 않는 죽은 필드
    [중간, 신규]

`AdoptionRecord.nextLoopNotes: readonly string[]`는 호출자가 손으로 채워 넣는 자유
텍스트이고(`demo.ts`에서 하드코딩된 문장 2개), `STRATEGY-HISTORY.md`의 "다음 루프
입력" 섹션에 그대로 출력될 뿐이다. `AdoptionLedger` 어디에도 이 필드를 생성/추론하는
로직이 없고, 어디서도 다시 읽어 다음 웨이브의 `candidates`를 채우는 데 쓰지 않는다
— 이름이 암시하는 "다음 루프의 입력"이라는 기능이 실제로는 존재하지 않는, 사람이
읽으라고만 있는 changelog 메모다. 목표 2의 "체계화된 루프"라는 표현과 가장 직접적으로
어긋나는 지점.

- **처치**: 최소한 near-miss 판정(`AdoptionEntry.verdict==='near-miss'`)을 구조화된
  형태(플래그, 실패한 축, 수치)로 뽑아내는 헬퍼를 만들어 "다음 후보 설계자가 참고할
  구조화된 목록"을 실제로 만든다. 자동 생성(ROADMAP v2)의 전 단계로 필요.

**의존 관계**: H5(Z3)를 풀면 H7이 자연스럽게 같은 설계 안에 들어간다. H8은 H6/H7이
해결된 뒤(게임별 네임스페이스 + 재로드 가능)에 만드는 게 순서상 맞다 — 안 그러면
요약할 대상 자체가 불안정하다. H9/H10은 서로 독립적이지만 함께 처리하는 게 효율적
(둘 다 "웨이브 결과 → 다음 설계 입력" 문제의 다른 절반).

**우선순위 제안**: H1(리포트 번역, 목표 1 핵심) → H5+H7(진입점+재로드, 목표 2
안정성의 기초) → H6(충돌 방지, 데이터 손상 위험) → H9+H10(큰루프 개입, 목표 2의
핵심 주장) → H8(통합 산출물) → H2(가이드 보강).
