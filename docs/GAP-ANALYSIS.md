# 갭 분석 — 훌라 · 체스 온보딩 리허설 (v1 → v1.1)

> 목적: 오픈소스로 확보한 훌라(럼미류 한국 카드게임)와 체스 프로젝트를 실제로 온보딩한다고
> 가정하고, 현재 파이프라인(v1, 커밋 d2c0f86)의 절차·장치가 충분한지 전수 점검한 기록.
> 각 갭에는 심각도와 처치(v1.1에서 구현 / 가이드로 해소 / 로드맵 이연)를 명시한다.

## A. 체스가 드러내는 갭 (완전정보 · 무작위성 없음 · 무승부 중심)

### A1. 시드 무의미 → 통계 전멸 [치명 · v1.1 구현]
체스는 초기 상태가 고정이라 `createInitialState(seed)`에서 시드가 할 일이 없다.
결정론적 봇 둘을 붙이면 **모든 시드에서 완전히 같은 게임**이 나오고, 600시드 페어드
블록은 사실상 표본 1개다 — 부트스트랩 CI·SPRT 전부 무의미해진다.
- **처치 1 (장치)**: 적합성 배터리에 **시드 다양성 검사** 추가 — 서로 다른 시드 M개의
  trajectory가 유의하게 달라야 한다. 결정론 게임 어댑터가 오프닝 다양성(시드 →
  오프닝북 라인 선택)을 구현하지 않으면 여기서 blocker가 뜬다.
- **처치 2 (가이드)**: ONBOARDING-GUIDE에 "무작위성 없는 게임은 시드-인덱스 오프닝북
  으로 초기 국면 다양성을 주입하라"(체스 엔진 테스트 표준 관행, Fishtest/OpenBench 동일)
  명시.

### A2. 완전정보 게임이 C3에서 부당 탈락 [치명 · v1.1 구현]
현재 C3는 `hiddenInfoProbe` 부재 시 0점 blocker다. 체스는 숨길 정보가 없으므로
probe를 만들 수 없다 → 영원히 ready 불가.
- **처치**: `GameSpec.perfectInformation: true` 선언 필드 추가(계약 변경). 선언 시
  C3는 만점 통과 + "완전정보 게임 — 은닉 검사 해당 없음" note. 선언 없이 probe도
  없으면 기존대로 blocker.

### A3. 무승부 지배 통계 [중간 · 가이드 + 로드맵]
비슷한 실력의 체스 봇끼리는 무승부가 지배적이다. 페어드 블록 winFraction에 0.5로
반영되므로 부트스트랩 게이트는 건전하지만, v1 SPRT는 베르누이 모델이라 무승부율이
높으면 검정력이 떨어진다.
- **처치**: INTERPRETATION에 한계 명시 + 무승부율을 리포트 지표로 노출(v1.1).
  GSPRT(pentanomial) 업그레이드는 ROADMAP v2 유지.

### A4. 게임 길이와 처리량 척도 왜곡 [중간 · v1.1 구현]
랜덤 봇 체스 플레이아웃은 수백 수까지 간다. games/sec 하나로 재는 C4는 "긴 게임"을
"느린 어댑터"로 오판한다. 또한 50수 규칙·3회 반복 무승부를 어댑터가 구현하지 않으면
종국하지 않는데, 이는 C2의 max-decisions defect로 잡히긴 하나 원인 안내가 없다.
- **처치**: C4를 games/sec + **decisions/sec 병기**로 바꾸고 감점 기준은
  decisions/sec 우선. C2 defect 메시지에 "종국 규칙(반복/무진행 무승부) 미구현 여부
  확인" remediation 추가.

## B. 훌라가 드러내는 갭 (은닉 정보 · 게임 중 셔플 · 3~4인 · 라운드제)

### B1. 게임 중간 무작위성(스톡 소진 → 버림패 재셔플) [중간 · 가이드 + 검사]
훌라는 스톡이 마르면 버림 더미를 재셔플한다. 계약상 상태는 불투명이라 가능하지만,
어댑터가 재셔플에 `Math.random()`을 쓰거나 RNG를 상태에 싣지 않으면 결정론(C1)이
깨진다. 초기 셔플만 시드로 하고 재셔플을 비결정으로 두는 실수가 전형적이다.
- **처치**: ONBOARDING-GUIDE에 "게임 중 무작위성은 `createInitialState`에서 fork한
  RNG를 상태에 보관해 소비하라" 패턴 명시. C1의 재현 검사는 이미 이 실수를 잡는다
  (재셔플에 도달하는 긴 게임 시드가 표본에 있는 한) — C1 표본에 **최장 게임 편향
  시드 선택**(가장 결정 수가 많은 시드 우선 재현)을 추가해 검출 확률을 높인다.

### B2. 3~4인 자유전의 페어드 통계 [높음 · v1.1 구현]
현재 `runPairedBlock`은 candidate 1명 vs 나머지 전좌석 동일 opponent 구조 자체는
3~4인을 지원하지만, 좌석 순열 요건("index 0이 모든 좌석 커버")이 4인이면 최소 4개
순열을 요구한다 — mini-trick(2인)에서만 검증됐고 3~4인 어댑터로 실검증된 적 없다.
- **처치**: 4인 테스트 픽스처(경량 더미 게임)로 paired-match·calibrate·wave-runner의
  다인수 경로를 회귀 테스트에 추가.

### B3. 팀 게임 점수차 오염 [높음 · v1.1 구현]
`runPairedBlock`이 `spec.teams`를 완전히 무시한다: 팀 동료 점수를 "상대 점수 평균"에
넣고, 공동 승자(팀 승리 = winners 2명)를 무조건 0.5로 계산한다. 훌라·체스엔 팀이
없지만 티추류를 온보딩하는 순간 승률이 전부 0.5로 뭉개진다.
- **처치**: 팀 인지 계산으로 수정 — winFraction: candidate 팀이 승자 집합과 일치=1,
  비팀원과 공동=0.5, 아니면 0. scoreDelta: candidate 팀 평균 − 상대 팀 평균.
  팀 없는 게임은 기존 동작과 동일해야 함(회귀 테스트).

### B4. 가변 인원 설정 [낮음 · 가이드]
훌라는 2~4인 가변. `GameSpec.playerCount`는 고정이다.
- **처치**: "어댑터 1개 = 게임 설정 1개"(예: hula-3p, hula-4p 별도 어댑터, 공통 로직
  공유) 원칙을 가이드에 명시. 계약 변경 없음.

### B5. 라운드제/매치제 경계 [낮음 · 가이드]
훌라는 점수 누적 다라운드 매치가 일반적이다. 루프의 게임 단위는 "독립적으로 채점
가능한 최소 단위"(=1딜)로 잡아야 통계 표본이 최대화된다.
- **처치**: 가이드에 명시. 매치 단위 평가가 필요하면 composite score에 반영.

## C. 두 게임 공통 — 산출물·반복 사용 갭

### C1. 산출물 영속화 부재 [치명 · v1.1 구현]
WaveReport는 메모리+digest뿐, 디스크에 남지 않는다. 반복 사용 시 "지난 웨이브 대비
무엇이 늘었는가"를 답할 수 없다.
- **처치**: `src/artifacts/` 신설 — 실행마다 `runs/<runId>/` 아래 canonical JSON +
  digest + 사람이 읽는 Markdown 리포트(표·유니코드 바 차트·SVG 추이 그래프) 기록.

### C2. 기준선 진화·전략 이력 부재 [치명 · v1.1 구현]
채택된 플래그를 다음 기준선으로 합성하는 장치(티추의 `V*_FLAGS` 상당)와 채택 이력
장부(`strategy-history.md` 상당)가 없다. 큰 루프가 상태를 가질 곳이 없다.
- **처치**: `BaselineRegistry`(버전드 플래그 셋 합성 — `StrategyFlagSpec.apply` 합성으로
  구현) + `AdoptionLedger`(웨이브별 채택/탈락 기록, STRATEGY-HISTORY.md 렌더) +
  **벤치마크 앵커**(동결 버전 봇 사다리로 절대 진행도 측정, 티추 ladder-v1 상당).

### C3. 점수 비교 가능성 규칙 부재 [높음 · v1.1 구현]
승률·점수차는 (상대, 시드 뱅크, 기준선, 어댑터 digest)가 같을 때만 비교 가능하다.
현재 리포트에 이 "비교 문맥"이 구조화돼 있지 않아 반복 사용 시 오해석 위험.
- **처치**: 모든 리포트에 `comparabilityKey`(위 4요소의 digest) 명시, INTERPRETATION
  문서에 해석 규칙 성문화.

### C4. 번들 후보 미지원 [중간 · v1.1 구현]
플래그 1개 단위 평가만 가능. 채택 후 "기준선+신규 플래그" 회귀 확인(티추의 marginal
check)을 하려면 플래그 합성 후보가 필요하다.
- **처치**: WaveConfig 후보를 `flags: string[]`(합성 순서 보존)로 확장.

### C5. 단일 상대 과적합 [중간 · 부분 구현 + 로드맵]
heuristic 하나만 상대로 평가하면 그 상대에게만 강한 전략이 채택된다(티추 ecology
veto의 교훈).
- **처치**: 벤치마크 앵커 사다리(random/heuristic/과거 기준선들)를 v1.1에 구현해
  채택 후 사다리 점수를 병기. 다상대 채택 게이트 자체는 ROADMAP v2.
