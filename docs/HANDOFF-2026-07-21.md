## 1. 이 프로젝트가 무엇인가

**Loop Forge** — 완성된 게임 프로젝트(보드게임·전략 카드게임)를 받아 그 게임의 NPC
난이도를 프롬프트 없이 자동으로 끌어올리는 플랫폼. 두 축:
1. **게임 온보딩 파이프라인**: G-Profile(파악) → G-Score(적합성 채점 C0~C7+커버리지)
   → G-Convert(headless 쌍둥이 구현) → G-Parity(정합성 증명). 임계 미달이면 루프 거부.
2. **큰 루프/작은 루프**: 후보 전략 설계(큰) → 좌석 미러링 페어 대국·SPRT·holdout
   시드 격리의 다단 게이트(작은)로 수십만 판 통계 검증 → 채택만 기준선 반영.

기원: 웹 티추 NPC 하네스(`/Users/treestar/dev/tichu`의 `harness/`, 후보 4,100개 ·
16만+ 판 · 과적합 발견 · 아키텍처 리셋)의 방법론을 게임 중립으로 일반화한 신규
프로젝트. 티추의 실사고(좌석 편향 +15%p, 고정 시드 과적합, ±7.9%p 노이즈 오채택,
관찰 오염)가 이 프로젝트의 채점 축·게이트 규칙의 직접 근거다.

## 4. 구조 지도

```
src/contract/types.ts   ① 계약 정본 — 결정 지점은 데이터, 봇은 decide() 하나.
                           perfectInformation, contentInventory/exercisedContent 포함
src/kernel/             ③ 게임 중립 커널 — rng, seed-ledger, paired-stats(+recommendBlockCount),
                           sprt, digest, comparability, gates(다단 게이트 판정)
src/loop/               ④ 루프 엔진 — match(결함 분류), paired-match(팀 인지),
                           calibrate(항등·노이즈·signalCollapseRate), compose, wave-runner
src/onboarding/         ② 적합성 게이트 — profile 스키마, score(C0~C7 배터리), report
src/artifacts/          산출물 — run-store, baseline-registry(+앵커), adoption-ledger,
                           benchmark(사다리), charts(유니코드 바·SVG)
src/reference/          mini-trick 레퍼런스 게임 + demo.ts
src/__tests__/          dependency-rules.test.ts — 계층·결정론 기계적 강제
docs/                   ONBOARDING-GUIDE(절차+계열별 규칙), INTERPRETATION(해석 성문),
                           GAP-ANALYSIS 1~3, HANDOFF(이 문서)
```

의존 방향 정본: `contract ← kernel ← loop ← onboarding`, `artifacts`는 loop/kernel 위,
`reference`는 contract+kernel/rng만, `demo.ts`만 앱 경계(전 계층 + 벽시계 허용).

## 5. 핵심 설계 불변 규칙 (위반 금지)

1. 게임 지식은 contract 위로 올라가지 않는다 (린트가 강제).
2. `Date.now()`/`Math.random()`은 demo(앱 경계) 밖에서 금지 — 타임스탬프는 호출자 주입.
3. smoke 통과는 채택이 아니다. holdout(미사용 예약 시드)까지 통과해야 adopted.
4. holdout/graduation 시드 뱅크 재사용 금지 — SeedLedger가 강제.
5. 앵커(동결 버전 봇)는 절대 갱신하지 않는다.
6. 점수 비교는 comparabilityKey가 같을 때만. 버전 간 비교는 앵커 사다리로만.
7. `spec.teams`는 고정·공개 팀 전용. 승/패 전용 게임은 `criteria.minScoreDiff=0`.

## 6. 다음 단계 (사용자가 예고한 작업)

**실전 게임 온보딩 테스트** — 오픈소스 게임 소스를 받아 실제 온보딩 후 봇 난이도 상승
루프 실행. 권장 순서(리스크 최소 경로, GAP-ANALYSIS-2/3 근거):

1. **스플랜더** (가장 싼 실전 검증: 콘텐츠 소량·은닉 단순·2~4인)
2. **오목** (신호 붕괴 대응 실전 검증 — signalCollapseRate·불균형 오프닝)
3. **장기** (결정론 게임 + 시드-강제 다양성)
4. **도미니언** (덱빌더·콘텐츠 커버리지 실전)
5. **윙스팬 core 부분집합 → 하스스톤** (증분 온보딩 전략)

온보딩 절차는 `docs/ONBOARDING-GUIDE.md`를 그대로 따른다: §0 적용 범위 확인 →
G-Profile(profile.ts 스키마 작성) → G-Convert(§2 체크리스트) → `scoreAdapter` 채점 →
blocker 수정 반복 → parity → 캘리브레이션(`recommendBlockCount`로 뱅크 크기 결정) →
SeedLedger 뱅크 예약 → `runWave` → AdoptionLedger/BaselineRegistry/앵커 사다리 갱신.

## 8. 미해결/로드맵 (ROADMAP.md + 갭 분석의 이연 항목)

- GSPRT(pentanomial) — 무승부 지배 게임의 SPRT 검정력 (체스류에서 필요해짐)
- 불균형 오프닝북 생성 도구 — X1 신호 붕괴의 근본 해법 (오목 온보딩 시 필요)
- 필드 믹스 웨이브 — FFA 킹메이킹 대응 (Y7)
- 소스 클로저 digest(런타임 identity), 분산 워커(OpenBench 모델), 큰 루프 자동화
- 솔로/협력 게임 지원, 덱 구성 탐색
- 레퍼런스 게임(mini-trick)은 no-op 플래그 동봉으로 C6이 67%라 데모 임계 65 사용 —
  실전 게임에는 기본 임계 70 적용
