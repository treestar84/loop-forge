# 온보딩 플레이북 — 명령과 프롬프트를 순서대로 따라하기

> 이 문서는 **절차서**다: 무엇을 치고, 코딩 에이전트에게 무엇을 붙여넣고,
> 어떤 숫자가 나오면 다음으로 가는지만 담는다. 각 단계의 "왜"와 심층
> 체크리스트의 정본은 [ONBOARDING-GUIDE.md](./ONBOARDING-GUIDE.md)이고,
> 게이트 수치의 근거는 [GAP-ANALYSIS-13.md](./GAP-ANALYSIS-13.md) §2·§2.5다.
> `npm run onboard`가 매 단계 끝에 "다음 행동"을 출력하므로, 길을 잃으면
> 인자 없이 `npm run onboard -- status <gameId>`를 치면 된다.

## 준비물 (시작 전 1분 자가진단)

- **내 게임의 소스코드** (또는 정확한 규칙 문서 — 코드가 있을수록 정확도가
  올라간다. 기존 봇/NPC는 **필요 없다**. 기준선 봇은 온보딩 과정에서 새로
  만들어진다.)
- 이 저장소 clone + `npm install` (Node 18+)
- 코딩 에이전트 (Claude Code 등 — 이 저장소를 읽고 쓸 수 있으면 무엇이든)
- 범위 3문항 — 하나라도 "아니오"면 여기서 멈춘다(자세한 제외 사유는
  가이드 §0): ① 턴제인가? ② 경쟁(2인 이상)인가? ③ 게임 간 상태가
  독립인가?

## 1단계 — 진단: 내 게임이 얼마나 준비됐는지부터 안다

```bash
npm run onboard -- <내 게임 소스 경로>
```

첫 실행이면 CLI가 **GameProfile 작성 프롬프트**를 출력한다. `claude` CLI가
설치돼 있으면 자동 실행을 시도하고, 아니면 출력된 프롬프트를 코딩
에이전트에 그대로 붙여넣은 뒤 같은 명령을 다시 친다.

**통과 기준 (G1)**: 프로필이 스키마 검증(`parseGameProfile`)을 통과하면
진단 리포트가 나온다:

| 리포트 항목 | 의미 |
|---|---|
| 판정 첫 줄 | **불가능** / **구현 필요** / **실행 가능** 중 하나 |
| 준비도 % | 어댑터가 없으면 **P-Score(추정)**, 있으면 **C-Score(실측)** — 라벨로 구분됨 |
| `runs/<gameId>/RULEBOOK.md` | 내 게임의 룰 시스템 분류 + **보완 구현 목록**(감점 큰 순) |
| 다음 행동 | 다음에 칠 명령과 에이전트 프롬프트 |

- **"불가능"이 나오면**: 사유서가 어느 전제(실시간/협력/캠페인/자유 협상)가
  왜 구현으로도 해결되지 않는지 설명한다. 여기서 끝 — 시간을 아낀 것이다.
- **"구현 필요"가 나오면**(정상 경로): RULEBOOK.md의 보완 목록을 읽고 2단계로.

## 2단계 — 스캐폴드: 어댑터 시작점을 자동 생성

```bash
npm run onboard -- scaffold <gameId>
```

프로필에서 아키타입(완전정보/은닉정보/멀티스텝턴/콘텐츠헤비, 조합 가능)을
자동 판정해 `src/reference/<gameId>.ts`(어댑터 골격)와
`src/reference/runners/<gameId>.ts`(러너)를 생성한다. 골격은 그 자체로
tsc를 통과하며, 채워야 할 곳마다 `TODO(onboard): §2-<번호>` 마커가 있다.

코딩 에이전트에게 (그대로 복사):

> `src/reference/<gameId>.ts`의 `TODO(onboard)` 마커를 전부 구현해줘.
> 각 마커의 §2-번호는 `docs/ONBOARDING-GUIDE.md` §2 체크리스트 항목이니
> 해당 항목을 읽고 그대로 따라줘. 원본 게임 소스(<경로>)는 참조 구현일
> 뿐이고 수정 대상이 아니야. 모든 무작위는 주입된 RNG로만(`Date.now()`/
> `Math.random()` 금지), 은닉 정보는 `getObservation`으로만 노출해줘.

**통과 기준 (G2)**: `TODO(onboard)` 마커 0개 + `npm run typecheck` 0에러.

## 3단계 — 채점 루프: 숫자가 통과라고 말할 때까지

```bash
npm run onboard -- score <gameId>
```

**이 단계는 1회로 끝나지 않는 게 정상이다** — 실제 온보딩된 9개 게임
전부 채점→수정→재채점을 여러 번 돌았다. blocker가 나오면 코딩 에이전트에게:

> `npm run onboard -- score <gameId>`의 blocker를 고쳐줘. 수정 대상은
> 어댑터 코드(`src/reference/<gameId>.ts`)이지 원본 게임이 아니야.
> 각 blocker의 remediation 문구가 무엇을 고칠지 알려줘.

**통과 기준 (G3)**: C7 제외 blocker 0개 (= overall ≥80, 결정론 재현 100%,
identity 50%±CI 포함). 이 시점부터 준비도 %는 추정이 아니라 **실측
C-Score**다.

- **C7이 60점이어도 정상**: 원본 게임에서 뽑은 리플레이가 없으면 정합성
  증명이 self-play 수준으로 격하돼 60점 캡이 걸린다. 온보딩을 막지 않고
  경고로만 표시된다. 원본 리플레이를 나중에 추가하면 캡이 풀린다.

## 4단계 — 첫 웨이브: 루프가 실제로 돈다

```bash
npm run onboard -- wave <gameId>
```

캘리브레이션(노이즈 플로어 → 판수 자동 권고) 후 첫 웨이브가 돈다.

**통과 기준 (G4 = 온보딩 완료)**: `WaveReport`와 `runs/<gameId>/summary.md`
생성. **후보 전략이 전부 탈락해도 온보딩은 성공이다** — 완료 조건은 "루프가
통계적으로 신뢰 가능하게 돌 수 있는 상태"이지 "채택이 나온 상태"가 아니다.
이후의 전략 강화 반복은 [DESIGN.md](../DESIGN.md) §6과
[GAP-ANALYSIS-11.md](./GAP-ANALYSIS-11.md)의 영역이다.

## 흔한 실패와 처방

| 증상 | 원인 | 처방 |
|---|---|---|
| C1(결정론) blocker | 어댑터/봇 어딘가에서 `Math.random()`/`Date.now()` 사용 | 전부 주입된 RNG(`createRng`)로 교체 — 의존성 테스트가 위치를 알려준다 |
| C3(정보 은닉) blocker | 관찰에 상대의 비공개 정보가 섞임 | `getObservation`에서 해당 필드 제거 후, "관찰 JSON에 상대 카드 id가 없다" 테스트 추가 (가이드 §2) |
| 게임이 끝나지 않고 최대 스텝 도달 | 종국 보장 규칙이 원본에도 없음 — 실제 사례: 스플랜더 자원 데드락 | 어댑터에 스테일메이트/턴 상한 규칙 합성 (가이드 §1의 종국 보장 항목) |
| identity 캘리브레이션이 50%에서 크게 벗어남 | 좌석별 유불리를 seatingPlan이 상쇄하지 못함 | seatingPlan의 좌석 순열 재검토 (가이드 §2) |
| scaffold가 "파일이 이미 존재" 거부 | 같은 gameId로 이전 시도 잔재 | 잔재를 직접 삭제하거나 다른 gameId 사용 — 덮어쓰기 방지는 의도된 동작 |
