# 트러블슈팅 — 반복되는 운영 함정과 해법

> 이 문서는 "다음 세션이 같은 실수를 처음부터 다시 겪지 않게" 하려고 존재한다.
> 전부 2026-07-23~28 세션에서 실제로 발생한 사고·버그·오해다. 새로운 함정을
> 발견하면 여기에 추가한다(줄을 지우지 않는다 — FIX-BACKLOG와 같은 누적 원칙).

## 1. 자원 사고 — 무거운 연산 병렬 실행으로 세션 중단

**증상**: 여러 에이전트가 각자 무거운 연산(MCTS 웨이브, 대량 벤치마크, MCCFR
학습)을 동시에 실행 → 메모리 고갈(여유 131MB까지 감소) → load average 66 →
세션 자체가 중단됨.

**원인**: "에이전트를 병렬로 여러 개 띄운다"와 "무거운 연산을 동시에 여러 개
돌린다"를 혼동. 에이전트(대화형 서브세션)는 여러 개 떠 있어도 무해하지만,
각 에이전트가 만드는 **실행 프로세스**(ts-node 웨이브 실행 등)가 동시에 여러
개 돌면 실제 CPU/메모리를 두고 경쟁한다.

**해법**: 무거운 연산은 **항상 동시 1개**. 모든 에이전트 지시서에 다음을
명시한다:
1. 실행 전 `ps aux | grep -E "ts-node.*<project>" | grep -v grep`로 확인.
2. `--max-old-space-size` 같은 힙 오버라이드 절대 금지(대신 반복 수를 계단식
   소량 측정으로 추정해서 정함 — 아래 §2).
3. `nice -n 10`으로 실행.
4. jest(테스트)는 연산과 동시 실행 금지.

**징후로 미리 알아채는 법**: 학습/시뮬레이션 반복 수를 "일단 크게" 잡고
돌리려는 계획이 보이면 멈춘다 — 항상 소량(예: 1만)으로 먼저 재보고 외삽한다.

## 2. 메모리 사용량 사전 추정 (계단식 측정)

**증상**: MCCFR 등 반복 학습을 "한 번에 100만 회" 같은 큰 수로 돌렸다가 힙
고갈로 죽음(1번 사고의 직접 원인이었던 사례).

**해법**: 본 실행 전 반드시 **3점 계단 측정**(예: 1만/3만/10만 반복)으로
`(반복수, infosetCount 또는 메모리)`의 선형 관계를 확인하고, 목표 메모리
한도(예: 1.5GB) 안에 드는 최대 반복수를 역산한다. 실측 사례: mini-trick
perfect-recall MCCFR에서 3점(1만/3만/10만)이 ~12 infosets/반복으로 매우
선형이었고, 이를 근거로 15만 반복(≈180만 infosets, ≈1.4GB)을 선택 — 외삽
예측이 실제 학습 결과(1,797,073 infosets)와 거의 정확히 일치했다.

## 3. "unknown strategy flag" — registry가 동적 플래그로 승격된 뒤 구 벤치마크 러너 실행

**증상**: `composeBot(adapter, flags)`를 원본(미확장) 어댑터에 호출했는데
`flags`에 `withStrategyFlags`로만 존재하는(정적 `strategySurface`에는 없는)
플래그가 섞여 있으면 "unknown strategy flag" 에러.

**원인**: 웨이브 러너는 `withStrategyFlags`로 어댑터를 확장해 탐색 후보 플래그
(`mcts-s64`, `ismcts-s128-hr` 등)를 주입한다. registry가 이 플래그를 포함한
버전으로 승격되면, **그 확장을 모르는** 구 벤치마크 러너(`<gameId>-
benchmark.ts`)가 `registry.latest().flags`를 읽어 그대로 `composeBot`에
넘기다가 원본 어댑터에는 없는 플래그를 만나 에러가 난다.

**해법**: registry 버전이 바뀔 때마다 벤치마크 러너도 **새 파일**로 만들어
`withStrategyFlags`로 확장한 어댑터에 `composeBot`을 호출하도록 한다(기존
구 버전 파일은 덮어쓰지 않고 보존 — `gomoku-benchmark-v4.ts`,
`hearthstone-benchmark.ts`(v2), `splendor-benchmark-v3.ts` 전부 이 패턴).

## 4. C3(은닉정보) 샘플러가 긴 셋업 구간 게임에서 0점

**증상**: 초기 배치 구간이 긴 게임(카탄의 16결정 스네이크 배치처럼)에서
`score.ts`의 C3 샘플러가 기본 옵션(`c3SampleStates`)으로는 표본을 하나도 못
뽑아 0점.

**원인**: 셋업 구간은 손패가 비어 있거나 은닉 정보 자체가 아직 존재하지 않는
상태라, 샘플러의 기본 탐색 창이 이 구간 전체를 못 뚫으면 은닉 정보가 있는
지점을 하나도 못 찾는다.

**해법**: 어댑터 본체(`score.ts`)를 고치지 말고, 러너 호출에서
`c3SampleStates`를 override(예: 25)해 탐색 창을 넓힌다. 채점기 문제인지
어댑터 문제인지 먼저 구분하는 것이 원칙(`ONBOARDING-GUIDE.md` §5.5) —
이번엔 채점기의 기본값 한계였지, 어댑터 버그가 아니었다.

## 5. identityCenter 자기모순 — 옵트인 선언 없이 숨은 진영/협동 게임 온보딩

**증상**: `scoreC5`가 무작위 자기대국 승률이 `1/playerCount`에서 벗어난다고
`C5_IDENTITY_NOT_FAIR` 블로커를 던지는데, 이게 **가이드를 정확히 따른** 결과일
수 있다(승리조건이 비대칭인 게임).

**해법**: `GameSpec.hiddenTeamStructure?`(숨은 진영) 또는
`cooperativeStructure?`(협동 게임)를 선언한다. `teams` 필드는 여전히
선언하지 않는다(불변 규칙: teams는 고정·공개 팀 전용). ADR-0006 참고.

**주의**: 이 옵트인은 "1/N 검사를 끈다"이지 "좌석 편향 검사를 끈다"가 아니다
— `identity.bias` 검사는 별도 경로로 그대로 살아있다.

## 6. 롤아웃 정책으로 쓰면 오히려 나빠지는 "단독으로 강한" 전략

**증상**: 단독 평가에서 base보다 나은 전략을 MCTS의 `rolloutFactory`로 감싸면
오히려 승률이 떨어짐(장기의 captureHighestValue+preferCheck 조합: 진단
head-to-head 0.1583, 이전 순정 heuristic 롤아웃의 0.375보다 나쁨. 도미니언의
챔피언 흉내 롤아웃도 규정 승률 0.275→0.100로 악화).

**원인**: "단독 결정"과 "롤아웃 시뮬레이션 안에서의 반복 사용"은 다른
맥락이다. 안전 검토 없이 "무조건" 실행되도록 설계된 전략(예: 위험 무시 포획)을
롤아웃에 쓰면, 시뮬레이션 내내 자멸적인 플레이 패턴을 만들어 MCTS가 그
왜곡된 보상 신호를 신뢰하게 된다.

**해법**: 롤아웃 후보를 정할 때 반드시 **진단(gate-free head-to-head, 소규모
N)으로 먼저 확인**한다 — "단독으로 좋아 보인다"만으로 웨이브에 바로 태우지
않는다.

## 7. 얕은 탐색이 결정론적 신호를 희석

**증상**: 게임 지식 기반 전략(예: 오목의 포크 인식)이 탐색 없이는 신호를
보이는데(9.0%, 최초 돌파), MCTS로 감싸는 순간 신호가 사라짐(0.0%).

**원인**: 트리 탐색의 시뮬레이션 예산이 분기수보다 작으면(오목 256sim vs
분기 ~220) 결정론적 확신이 통계적 잡음 안에 묻힌다.

**해법**: `tacticalDepth`(즉승/즉패)처럼 **탐색을 아예 건너뛰는 루트
오버라이드 훅**(`rootOverride`, ADR-0008)을 시도해볼 가치가 있다 — 단, 이걸로도
안 되면(오목 사례) 그 신호 자체의 한계일 수 있다는 것을 계측(실제 발동
빈도 확인)으로 검증하고 정직하게 결론 내려야 한다.

## 8. ts-node 직접 실행 시 확장자 에러

**증상**: 스크래치 스크립트를 `node <file>.ts`로 직접 실행 시
`TypeError: Unknown file extension ".ts"`.

**해법**: 항상 `npx ts-node <file>.ts`(또는 `nice -n 10 npx ts-node
<file>.ts`)로 실행한다. 프로젝트 루트 밖(`/private/tmp/.../scratchpad`)에
스크립트를 두고 상대경로 import를 쓰면 ts-node가 tsconfig/모듈 해석을 못하는
경우도 있었다 — 무거운 실험 스크립트는 프로젝트 내부의 임시 디렉토리(예:
`scratch-*/`, 작업 종료 후 삭제)에 두는 편이 안전하다.

## 9. 저장소 루트에 스크래치 파일이 남는 문제

**증상**: 에이전트가 스크래치 스크립트를 세션 스크래치패드가 아니라 저장소
루트(`scratch-n4/`, `scratch-b2/` 등)에 만들어 `git status`에 계속 잡힘.

**해법**: 매 라운드 마무리 시 `git status --short`로 미추적 디렉토리를 확인해
정리한다(`.omc/`는 예외 — 항상 커밋 제외 대상). 에이전트 지시서에 스크래치
경로를 세션 스크래치패드로 명시했는데도 발생할 수 있으니 마무리 단계에서
한 번 더 확인.

## 10. 유휴(idle) 서브에이전트는 좀비 프로세스가 아니다

**오해**: 여러 서브에이전트가 "idle" 알림을 보내면 자원을 낭비하고 있다고
오인하기 쉽다.

**사실**: 유휴 알림은 "할 일을 마치고 대기 중"이라는 뜻이지 OS 프로세스가
남아 도는 게 아니다. 진짜 확인할 것은 `ps aux | grep ts-node` 같은 실행
프로세스뿐이다. 다 쓴 에이전트 스레드는 `TaskStop`으로 정리해도 되지만
안 해도 자원을 쓰지 않는다.

## 11. 병렬 에이전트의 파일 변경 선별 커밋

**문제**: 두 에이전트가 동시에 다른 파일을 건드리고 있을 때 `git add -A`로
한꺼번에 커밋하면, 아직 작업 중인(미완료) 다른 에이전트의 파일까지 같이
커밋될 위험이 있다.

**해법**: 항상 `git status --short`로 어떤 파일이 어느 라운드 것인지 확인한
뒤, 완료된 라운드의 파일만 `git add <구체적 경로>`로 선별 스테이징한다.
`git add -A`는 두 라운드가 확실히 독립적일 때만.

## 12. 테스트 스위트 시간 예산 — 회귀 다이제스트 테스트가 조용히 누적된다

**문제**: `npm test`가 이 저장소의 오랜 관행상 12~13초대였는데, GAP-11
라운드에서 "기존 registry 합성봇의 재현이 편집 전후 완전히 동일함"을
증명하는 회귀 테스트(30시드 실제 MCTS self-play × 여러 registry)를 매번
"당장은 합리적"이라며 추가하다 보니 어느 순간 **438.9초**까지 누적됐다
(GAP-ANALYSIS-12 §0.4). 개별 결정은 전부 타당했지만("이 안전장치는 꼭
필요하다") 누적 비용에 대한 상한이 없어 전체가 나빠졌다.

**해법**: 무거운 회귀 테스트(실제 게임 self-play·다중 시드 다이제스트 비교
등)를 추가하기 전에 반드시:
1. `npm test` 전체 시간을 먼저 재둔다(전/후 비교 기준).
2. 그 테스트의 목적이 **통계적 검증**(승률 추정 등, 시드 수가 신뢰도에
   비례)인지 **결정론적 동일성 검증**(코드 경로가 안 바뀌었다는 증명, 시드
   수가 신뢰도에 기여하지 않음)인지 구분한다 — 후자라면 3~5시드로 충분하다
   (30시드와 신뢰도 차이가 없다).
3. 추가 후 전체 시간이 눈에 띄게(예: 두 배 이상) 늘었으면, 그 자리에서
   즉시 시드 수·범위를 줄여 맞춘다 — "다음에 정리하자"로 미루지 않는다.
4. 대략 30초를 넘기지 않는 것을 기본 감으로 삼는다(2026-07-30 GAP-12 E1
   작업에서 이 규칙을 적용해 54초대를 46.7초로 되돌린 실측 사례가 있다).

무거워도 되는 유일한 예외는 "실제 사고를 재현/방지하는 다이제스트 회귀"처럼
안전 가치가 명백할 때뿐이고, 그 경우에도 §2번 판단(시드 수를 줄여도 되는
성격인지)은 항상 먼저 한다.

## 13. 초월 근접실패는 후보를 다시 설계하기 전에 검정력부터 의심하라

**문제**: 오목 v9(`mcts17-s256-clone-earlyprior-sched`)가 같은 후보로
세 번 독립 측정됐는데(round5 N=100 55.5%, round5 N=200 확증 53.1%, round6
N=100 재확인 54.3%) 점추정은 매번 53~55%로 일관됐지만 CI 하한이 두 번
연속 0.5 문턱 바로 아래(49.8%)에서 걸렸다. "설계가 부족해서 못 넘는다"고
해석해 재설계 라운드를 두 번 더 돌렸지만(오목 5·6회전), 실제 원인은 후보가
아니라 **확증 표본 크기의 검정력 부족**이었다 — N=1,000으로 올리자 같은
후보의 점추정은 그대로(53.67%)인데 CI 폭만 ±3.4%p→±1.5%p로 좁아지며 하한이
52.18%로 확실히 넘어 초월이 확정됐다(`docs/GAP-11-ROUNDS.md` "오목 v9
대규모 확증"). 세 번의 점추정이 전부 50%를 넘겼는데 하한만 반복해서
문턱에 걸린다는 신호를, 그때마다 "후보를 다시 설계해야 한다"는 신호로
오독했던 것이다.

**해법**: 같은 후보(설계를 바꾸지 않은 동일 flags)의 초월 사다리가
연속으로(2회 이상) CI 하한만 문턱 근처에서 걸리고 점추정 자체는 매번
0.5를 넘는다면, 다음 라운드로 넘어가 새 후보를 설계하기 **전에** 먼저
확인한다:
1. 지금까지 측정한 N이 얼마인지, 그리고 그 N에서 나온 CI 폭이 "0.5와
   분리하기에 충분한지"부터 계산해본다 — 점추정과 0.5 사이의 거리가
   CI 폭의 절반보다 작으면 표본 부족이 원인일 가능성이 높다.
2. 새 설계를 시도하기 전에, **같은 후보를 그대로 훨씬 큰 N(예: 기존의
   5~10배, 이 저장소의 벤치마크급 규모인 N=500~1,000)** 으로 한 번
   재확인한다 — 이게 설계 라운드보다 싸다(새 후보 설계·구현·전 티어
   게이트 통과 없이 순수 재측정 한 번이면 된다).
3. 그래도 하한이 못 넘으면 그때 설계 문제로 넘어간다 — 이 순서를
   뒤집어서 "일단 다시 설계"부터 하면, 검정력 문제였을 경우 여러 라운드를
   낭비하게 된다(오목이 실제로 그랬다).

이 규칙은 초월 판정뿐 아니라 일반적인 근접실패(near-miss) 반복에도 적용된다
— "같은 문턱에서 반복 근접실패"는 설계 신호가 아니라 통계 신호일 수 있다는
것을 항상 먼저 배제하라.
