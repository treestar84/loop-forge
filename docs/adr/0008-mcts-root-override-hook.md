# ADR-0008 — MCTS에 게임 중립 루트 오버라이드 훅 신설

**상태**: 채택됨 (2026-07-27)

## 맥락

오목에서 다방향 위협(포크) 인식 전략(`forkAwareness`)을 만들었더니, 탐색 없는
순정 휴리스틱으로는 챗봇 AI 상대 9.0%(최초 0%대 돌파)를 기록했지만, 이걸 MCTS
롤아웃 정책으로 감싸는 순간 다시 0.0%로 떨어졌다. 원인: 얕은 트리 탐색(256
시뮬레이션, 분기계수 ~220)이 포크 판정의 결정론적 확신을 통계적 잡음으로
희석시킨다. `tacticalDepth`(즉승/즉방어 판정 시 탐색을 아예 건너뛰는 기존
훅)와 똑같은 문제를 포크 판정에서도 겪은 것이다.

## 결정

`search/mcts.ts`의 `MctsConfig`에 `rootOverride?: (adapter, state, legal,
player) => choice | null`을 추가한다. 호출 순서: `tacticalDepth`의 즉승 체크
(최우선, 리터럴 승리가 항상 이겨야 함) → `rootOverride` → `tacticalDepth`의
2-ply 안전망 → 일반 MCTS. non-null 반환 시 시뮬레이션 없이 즉시 반환. 훅
자체는 게임을 전혀 모르는 인프라(`search/mcts.ts`에 위치)이고, 실제 포크
판정 함수는 게임 지식이라 어댑터(`reference/gomoku.ts`)에만 둔다 —
`rolloutFactory`/`tacticalDepth`와 같은 "어댑터 훅 주입" 패턴의 연장.

## 대안

- **포크 판정을 kernel/search에 하드코딩**: 기각 — 계층 규칙 위반(게임 지식이
  search로 샘). 훅 형태로 일반화해야 다음 게임도 재사용 가능.
- **시뮬레이션 예산을 낮춰 결정론적 우선순위의 영향력을 보존**: 검토 후 이연
  — "탐색 자체를 우회"가 더 원칙적인 해법이라 먼저 시도했고, 예산 조정은 다음
  카드로 남김.

## 결과

계측(`rootOverride` 호출 202회 중 83회 실제 발동, 41.1%)으로 배선이 정확히
작동함을 확인했음에도 **여전히 0.0%** — 정직한 부정적 결과. 그러나 훅 자체는
게임 중립 인프라로 유지 가치가 있고(다음 게임에서 재사용 가능), 단위테스트
5건으로 동작이 고정돼 있다. "탐색을 우회해도 안 되면 그 신호 자체의 한계"라는
결론까지 도달한 것이 이 ADR의 실질적 성과 — 오목 C열 문제가 배선/구현 결함이
아니라 더 근본적인 무언가(포크의 좁은 정의, 또는 나머지 수순의 탐색 실력)임을
증명했다.
